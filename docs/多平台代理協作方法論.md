# 多平台 AI 代理協作方法論

**目的**：Claude Code 負責「詳細規劃」（讀 codebase、拆解任務、寫出精確的任務規格），實際「動手實作」則交給本機已安裝的其他 CLI 代理（`copilot`、`agy`）執行，藉此降低 Claude Code 主對話的 token/context 消耗，同時保留 Claude Code 對品質與正確性的把關角色。

**本文件基礎**：由 agy（gemini-flash-high，grounded search）於 2026-08-12 檢索 2025～2026 年業界/社群討論整理而成，並依本機實際可用工具（`copilot` CLI、`agy-bridge`）落地為具體操作方式。原始檢索結果見文末「參考來源」。

---

## 一、四種主流整合方式

### 方法 1：Non-Interactive Shell Script（單次無狀態呼叫）

Claude Code 寫好任務規格後，直接透過 Bash 呼叫其他 CLI 的非互動模式（如 `copilot -p "..." --allow-all-tools`、`agy-bridge --type implement -- "..."`），一次性取得執行結果。

- **優點**：實作極簡；Worker 的內部推理（CoT）完全在 Worker 自己的進程內消耗，**完全不進入 Claude Code 的 context window**；沒有額外協定開銷；可直接用 `git diff` / 測試指令驗證結果。
- **缺點**：Worker 沒有跨呼叫的 session 記憶，多輪修改需要每次重新把背景資訊帶進 prompt；依賴 stdout/stderr 的乾淨程度，雜訊需自行過濾。
- **緩解方式：用一份 log md 檔案取代 session 記憶**——每次呼叫 Worker 後，要求 Worker（或由 Claude Code 事後）把「這輪做了什麼、改了哪些檔案、遇到什麼問題、下一步該注意什麼」摘要寫進固定的紀錄檔（例如 `<task>_log.md`）。下一輪呼叫 Worker 時，把這份 log 的內容（或其中相關段落）一併放進 prompt。這樣 Worker 本身仍是無狀態、乾淨的單次呼叫，但透過檔案系統銜接了跨呼叫的「記憶」，且這份 log 本身也是 Claude Code 事後檢查進度的依據，不需要重新翻 git log 或猜測前幾輪做了什麼。
  - log 檔建議只留「決策與結果摘要」，不要整段貼 Worker 的原始輸出，否則下一輪 prompt 又會把雜訊帶回來，失去省 token 的意義。
  - 這與方法 3（MCP）的差異在於：log md 是最輕量的手動作法，不需要額外中介服務；工作變頻繁、需要嚴格結構化時，才值得升級成 MCP server 內建的狀態管理。
- **Token 特性**：**主 context 消耗極低，全系統總 token 也最省**——沒有框架開銷、沒有反覆對話的浪費。log 檔案只在需要銜接上下文時才讀入，比讓 Claude Code 全程盯著 Worker 對話省更多。

### 方法 2：沙盒 / 子進程模擬互動式 CLI（PTY + expect）

在子進程開一個虛擬終端機（如 `node-pty`、`pexpect`），Claude Code 模擬使用者鍵盤輸入，跟一個保持開啟的互動式 CLI 對話。

- **優點**：Worker 可保留連續對話的 session 狀態，適合需要漸進式來回調整的場景；也適用於沒有良好非互動旗標的工具。
- **缺點**：**非常脆弱**——容易被 ANSI 轉義碼、進度條、CLI 改版、終端機寬度變化打斷卡死；出錯後極難自動修復；raw 終端輸出若原樣回傳給 Claude Code 會嚴重污染 context。
- **Token 特性**：主 context 消耗高（雜訊多），全系統總消耗中高（長 session 累積 + 卡死重試）。
- **結論**：不建議作為預設方式。

### 方法 3：MCP（Model Context Protocol）包裝為工具

把 Worker CLI 包成一個 MCP server，暴露強型別 tool（例如 `run_agy_task(prompt, files)`），Claude Code 用 `claude mcp add` 原生載入。

- **優點**：標準化、強型別，減少參數格式錯誤；MCP server 可在回傳給 Claude Code 前先做過濾、截斷、格式化，屬於工程化最佳解之一。
- **缺點**：**每個載入的 MCP server 的 JSON Schema 都會常駐注入到每一輪對話的 system prompt**，形成「閒置稅」（idle context tax）；需要額外維護一層中介服務。
- **Token 特性**：主 context 消耗中等（固定 schema 開銷 + 乾淨回傳），全系統中等。
- **適用時機**：任務極度頻繁、需要嚴格型別驗證、值得投入維護成本時再採用。目前本環境沒有現成的 agy/copilot MCP wrapper，屬於「未來可升級」選項，非當下首選。

### 方法 4：Orchestrator-Worker 框架 / Claude Code 原生 Subagent（Task/Agent tool）

外部框架（LangGraph、CrewAI、AutoGen）或 Claude Code 內建的 `Agent`/Task 工具，由 Orchestrator 節點分派高階指令，Worker 節點各自在獨立 context 中運作，完成後只回傳摘要。

- **優點**：**主 context 幾乎零污染**（Worker 在完全獨立的 context window 運作，只回傳 summary）；適合大型、需要平行處理或人工審核節點的複雜專案。
- **缺點**：開發/維護複雜度最高；多個獨立 LLM session 各自展開推理，**全系統 API 總消耗量最大**。
- **Token 特性**：主 context 極低，但全系統總 token 高。
- **本環境對應**：Claude Code 的 `Agent` 工具（`subagent_type`）本身就是這個模式，但呼叫對象是 Claude 模型本身的子代理，並非把任務轉包給 `copilot`/`agy`——兩者可以疊加使用（見下方建議架構），但不能互相取代。

## 二、橫向比較矩陣

| 維度 | (1) Shell Script | (2) PTY 模擬 | (3) MCP Wrapper | (4) Orchestrator/Subagent |
|---|---|---|---|---|
| 實作複雜度 | 極低 | 高 | 中 | 高 |
| 運行穩定度 | 高 | 極低（易卡死） | 極高 | 極高 |
| Worker 對話狀態保留 | 無（單次） | 有 | 可選 | 視設計而定 |
| Claude 主 context 消耗 | **極低** | 高（ANSI 雜訊） | 中（schema 稅） | 極低 |
| 全系統總 token 消耗 | **最省** | 中高 | 中 | 最高 |
| 推薦度 | ★★★★（本環境首選） | ★（不建議） | ★★★★（未來可升級） | ★★★★（大型專案疊加使用） |

## 三、結論：最省 token 又效果最好的方法

**首選：方法 1（Non-Interactive Shell Script）作為預設執行路徑**，搭配「結果導向驗證」取代「多輪對話式監工」：

```
[ Claude Code：規劃者 ]
        │
        ├─ 1. 讀 codebase、產出精確任務規格（明確檔案、範圍、驗收條件）
        │
        ├─ 2. 呼叫非互動 Worker 執行實作
        │      copilot -p "<task spec>" --allow-all-tools
        │      或
        │      agy-bridge --type implement -- "<task spec>"
        │
        ├─ 3. 本地驗證結果（不聽 Worker 自述，只看事實）
        │      git diff   （檢查改動範圍是否符合預期）
        │      測試指令    （功能是否正確）
        │      → 若失敗，把「錯誤訊息 + git diff」原樣餵回 Worker 做第二輪，
        │        而不是重新描述整個任務
        │
        └─ 4. 把這一輪的摘要（做了什麼／改了哪些檔案／下一步注意事項）
               追加寫入 <task>_log.md
               → 下一輪呼叫 Worker 前，把 log 相關段落帶進 prompt，
                 銜接跨呼叫的「記憶」
```

> **已落地為正式 Claude Code plugin**：log 資料夾路徑公式、檔名格式、log 內容模板、以及「僅限最上層 session 使用、避免子代理無限轉包」的限制，已包成本 repo（[LawrenceCHH/agent-delegation](https://github.com/LawrenceCHH/agent-delegation)）的 `skills/agent-delegation/SKILL.md`。換機器安裝只要：
> ```bash
> claude plugin marketplace add LawrenceCHH/agent-delegation
> claude plugin install agent-delegation@agent-delegation
> ```
> 之後用 `claude plugin update agent-delegation` 拉更新，不需要手動比對檔案或改 `~/.claude/CLAUDE.md`（marketplace 安裝的 plugin 會自動被 Claude Code 讀取，不像 skills-dir 手動複製那樣需要另外加 pointer）。之後任何專案的 Claude Code session 委派任務給 agy/copilot 前，都應先讀這份 skill，而不是重新發明格式。

**為什麼這樣最省又有效**：
1. 沒有 MCP schema 常駐開銷。
2. Worker 的思考過程、檢索雜訊完全留在 Worker 自己的 process 裡，回傳給 Claude Code 的只有最終 diff/結果——context 零污染。
3. 用 `git diff` / 測試取代「跟 Worker 對話確認」，比多輪來回對話省下大量 token（此為 agy 檢索報告估計節省幅度，屬概略參考而非精確量測：約 70%～90%）。
4. 用一份輕量 log md 檔案取代 Worker 的 session 記憶（見方法 1 說明），多輪任務不必每次重新鋪陳背景，也不必為了保留記憶而改用高開銷的 PTY 常駐或 MCP 狀態管理。

**何時該疊加方法 4（Claude Code 的 `Agent` 工具）**：當一個任務本身要拆成多個彼此獨立、可平行進行的子任務時（例如同時研究三個不同模組），才用 Claude Code 原生 `Agent` 工具開多個子代理分頭進行——但每個子代理內部呼叫 `copilot`/`agy` 實作時，仍應遵循方法 1 的模式。**不要**用方法 2（PTY 模擬互動）去操作 `copilot`/`agy`，除非該工具確實沒有可用的非互動旗標。

**何時該升級到方法 3（MCP）**：如果未來這類委派變得非常頻繁（例如每天呼叫數十次 `agy-bridge`/`copilot -p`），且愈來愈需要嚴格的輸入輸出格式驗證，可以考慮把 `agy-bridge` 包成一個只有 1～2 個 tool 的輕量 MCP server，用型別化介面取代目前手寫 prompt 字串的方式。

## 四、本環境落地備忘

已安裝、可直接用方法 1 呼叫的兩個平台：

| 工具 | 呼叫方式（非互動） | 適合任務 |
|---|---|---|
| `copilot`（GitHub Copilot CLI） | `copilot -p "<prompt>" --allow-all-tools` | 一般程式碼實作、檔案編修，多種模型可選（見 `copilot help config` 的 model 清單） |
| `agy`（Google Antigravity CLI，經 `agy-bridge` 包裝） | `agy-bridge --type search\|code\|analysis\|review\|implement -- "<prompt>"` | `search`＝gemini-flash-high 網路檢索；`code`/`implement`/`analysis`/`review`＝gemini-pro-high，適合大檔案分析、第二意見、實作 |

任務指派時的規格要包含：目標檔案路徑、明確的驗收條件（測試指令或可觀察行為）、以及不要做的事（避免 Worker 過度發揮）。這份規格本身就是 Claude Code「規劃」階段的產出，應該詳細到讓 Worker 不需要反問即可動手。

**跨呼叫記憶檔案慣例**：多輪委派同一任務時，在任務目錄下建立 `<task>_log.md`，每輪結束後追加一段（時間戳、做了什麼、改了哪些檔案、驗證結果、下一步待辦），只寫摘要不貼原始輸出。下一輪呼叫 Worker 前，Claude Code 讀取這份 log 並把相關段落塞進 prompt，取代「讓 Worker 常駐保留 session」的做法。任務結束後這份 log 可以直接刪除或併入 commit message，不需要長期保留。
